# 개인 포트폴리오 웹사이트 설계

## 1. 목표

백엔드 개발을 중심으로 서비스 화면과 클라우드 인프라까지 연결해 본 경험을 보여주는 공개 포트폴리오를 만든다. 채용 담당자는 메인 페이지에서 지원자의 방향과 대표 경험을 빠르게 파악할 수 있고, 기술 면접관은 프로젝트 상세 페이지에서 아키텍처, 기술적 판단, 트러블슈팅 근거를 확인할 수 있어야 한다.

사이트는 참고 사이트인 `min-hyuk.com`의 넓은 여백, 큰 타이포그래피, 실제 결과물 중심 구성에서 방향을 가져오되 동일하게 복제하지 않는다. 한정현의 프로젝트와 자료에 맞는 독립적인 정보 구조와 시각 체계를 사용한다.

## 2. 대상과 포지셔닝

### 주요 대상

- 백엔드 개발자 채용 담당자
- 클라우드·플랫폼 엔지니어 채용 담당자
- 기술 면접관과 실무 개발자

### 핵심 메시지

> 백엔드를 중심으로 API와 데이터 흐름을 설계하고, 사용자가 만나는 화면부터 실제 서비스가 동작하는 클라우드 인프라까지 연결해 본 개발자

풀스택과 클라우드 경험은 별개의 직무를 나열하는 용도가 아니라, 백엔드 기능이 실제 사용자 경험과 운영 환경에서 어떻게 완성되는지 이해하고 있다는 근거로 사용한다.

## 3. 공개 범위

초기 버전은 한국어 단일 사이트로 제작한다. 이름, 직무 방향, 프로젝트, 교육, 기술 역량, GitHub 링크와 연락 수단을 공개한다. 전화번호, 집 주소, 비공개 인프라 주소, 계정 정보, 토큰, 내부 IP 등은 포함하지 않는다.

연락처와 이력서 파일은 배포 직전 사용자가 최종 확인한 값만 노출한다. 자료 화면에 이메일, 이름, 계정, 클러스터 주소 등 불필요한 개인정보가 있으면 크롭하거나 마스킹한다.

## 6. 프로젝트 상세 페이지

모든 상세 페이지는 같은 읽기 순서를 사용하되 프로젝트 규모에 맞춰 분량을 조정한다.

1. 프로젝트 요약: 기간, 인원, 역할, 한 문장 설명
2. 문제와 목표: 왜 만들었고 어떤 사용 문제를 해결했는지
3. 기여 범위: 팀 전체 결과와 개인 담당 영역 구분
4. 서비스 화면: 실제 사용 흐름을 대표하는 화면
5. 아키텍처: 시스템 구성과 주요 데이터·요청 흐름
6. 핵심 구현: 중요한 기술적 판단 2~4개
7. 트러블슈팅: 문제, 원인, 해결, 검증 결과
8. 결과와 회고: 얻은 결과와 다음 개선점
9. 증빙: GitHub 저장소와 대표 PR·커밋·문서

프로젝트 상세 페이지는 기술 스택을 길게 나열하기보다 선택 이유와 연결 관계를 설명한다. 팀 프로젝트는 반드시 `팀 전체 구성`과 `내가 담당한 구성`을 구분한다.

## 7. 프로젝트별 아키텍처

### 공통 표현 규칙

- 저장소 코드, 배포 설정, 문서에 확인되는 구성만 표시
- 실제 제품 아이콘 또는 공식적으로 허용된 단순 로고 사용
- 좌우 요청 흐름과 상하 보조 흐름을 구분
- 교차선과 곡선을 최소화하고 직각 연결선 사용
- 사용자 요청은 파랑, 내부 데이터·검증은 초록, 장애 전환·복구는 보라 계열로 구분
- 모든 선에는 의미 있는 짧은 라벨을 표시
- 아키텍처 전체와 개인 담당 영역을 별도로 표시
- 모바일에서는 작은 다이어그램을 억지로 축소하지 않고 확대 가능한 이미지와 텍스트 요약 제공

### Cledyu

사용자 요청, AWS Edge, Caddy/Tailscale, Traefik, Next.js Web, Go Session API, Session Dispatcher, KubeVirt VM, PostgreSQL, Kafka, Validation Engine, Keycloak, AI Tutor, EC2 Overflow와 EKS DR의 관계를 보여준다. Vault, ESO, Argo CD, Prometheus, Grafana, Cilium/Hubble 같은 운영 제어면은 사용자 요청 흐름과 분리된 보조 아키텍처로 제공한다.

### CodeBuddy

GitHub Webhook, API Gateway, Lambda, 분석 단계, Amazon Bedrock, 결과 생성, GitHub 또는 Slack 전달 흐름을 보여준다. 실패한 CI 로그 처리, 민감정보 제거, 긴 패치 보존 같은 백엔드 판단을 아키텍처 아래에서 설명한다.

### Kagoshima Travel

React PWA, Go API, PostgreSQL, 인증, 여행 일정·체크리스트·공유 링크, 지도 연결, Oracle VM 배포 구조를 보여준다. 실제 사용자 관점의 모바일 흐름과 백엔드 데이터 흐름을 함께 연결한다.

### Chilseongpa

GCP 주 환경과 AWS 대기 환경, 네트워크 연결, 모니터링, 장애 전환과 복구 흐름을 보여준다. 팀 전체 하이브리드 구조와 사용자가 담당한 AWS 인프라·연결·모니터링 영역을 구분한다.

### PR Check Doctor

GitHub Actions 실행, 실패 로그 수집, 민감정보 제거, 규칙 기반 분류, 결과 요약, 단일 PR 코멘트 갱신 흐름을 보여준다.

## 8. 시각 디자인

### 방향

- 밝은 아이보리 또는 거의 흰 배경
- 검정에 가까운 본문색과 차분한 회색 보조색
- 한 가지 절제된 포인트 컬러
- 큰 제목, 넓은 여백, 얇은 구분선
- 실제 화면과 아키텍처를 크게 보여주는 에디토리얼 레이아웃
- 무의미한 그라데이션, 유리 효과, 과도한 pill, AI 생성 장식 배제

### 타이포그래피

- 한글 본문과 제목은 가독성이 검증된 한 개의 산세리프 패밀리 사용
- 영문·숫자 메타 정보에는 필요할 경우 모노스페이스 한 개만 보조 사용
- 본문은 좌측 정렬하고 한 줄 길이를 제한
- 굵기는 Regular, Medium, Bold 세 단계 이내로 제한

### 인터랙션

- 프로젝트 카드의 이미지 이동과 짧은 reveal 정도만 사용
- `prefers-reduced-motion`에서 모든 비필수 애니메이션 제거
- hover 없이도 모든 정보와 링크를 사용할 수 있어야 함
- 키보드 포커스와 색상 대비를 명확히 제공
