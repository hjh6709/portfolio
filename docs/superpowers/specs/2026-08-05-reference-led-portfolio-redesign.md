# Reference-led Portfolio Redesign Spec

## 1. 목표

현재 포트폴리오를 단순한 프로젝트 목록이 아니라, 한정현이 어떤 문제를 맡았고 어떤 기술적 판단으로 해결했는지 실제 화면과 근거로 확인할 수 있는 백엔드·클라우드 중심 포트폴리오로 개편한다.

`min-hyuk.com`의 강점인 긴 호흡의 편집형 구성, 큰 실제 화면, 프로젝트별 문제 해결 서사는 참고한다. 시각적 복제는 하지 않고 Cledyu를 비롯한 실제 작업 자료와 한정현의 경험에 맞는 정보 구조를 만든다.

## 2. 독자와 전달할 인상

주 독자는 백엔드 개발자 또는 클라우드 인프라 직무의 채용 담당자와 실무 면접관이다. 첫 화면과 대표 프로젝트를 통해 다음 내용을 빠르게 이해할 수 있어야 한다.

- 백엔드를 중심으로 API, 데이터, 인증, 세션 수명주기를 구현했다.
- 프론트엔드 화면과 사용자 흐름도 직접 설계하고 개선했다.
- Kubernetes, KubeVirt, AWS, GitOps 등 실제 배포 환경까지 확인했다.
- 기능 구현보다 문제의 원인, 기술 선택, 검증 결과를 설명할 수 있다.

## 3. 디자인 원칙

- 밝은 오프화이트 배경과 검정 계열 타이포그래피를 기본으로 한다.
- 파란색은 링크, 상태, 핵심 결과처럼 의미가 있는 위치에만 쓴다.
- 카드와 테두리를 반복하기보다 여백, 글자 크기, 실제 이미지로 계층을 만든다.
- 실제 서비스 화면을 아키텍처 다이어그램보다 먼저 보여준다.
- 아키텍처는 장식이 아니라 요청 흐름과 기술 판단을 설명하는 근거로 사용한다.
- 프로젝트마다 동일한 문구를 반복하지 않고 실제 작업 내용에 맞는 제목과 설명을 쓴다.
- 근거 없는 성과 수치, 과장된 표현, 추상적인 AI 문체를 사용하지 않는다.
- 긴 본문은 좌측 정렬하고 한 문단의 폭을 읽기 쉬운 범위로 제한한다.
- 모바일에서는 이미지와 본문을 단일 열로 배치하고, 핵심 링크의 터치 영역을 확보한다.

## 4. 홈 화면 구조

### 4.1 인트로

이름과 직무 포지셔닝을 짧게 제시한다. 현재의 긴 자기소개보다 아래 메시지를 명확하게 전달한다.

- Backend Developer
- 사용자 흐름을 서비스와 인프라까지 연결한 경험
- GitHub, 이력서, 이메일 접근

### 4.2 대표 프로젝트

소개 직후 대표 프로젝트를 배치한다. Cledyu를 첫 번째이자 가장 큰 사례로 보여준다.

각 프로젝트 항목은 다음 정보를 포함한다.

- 실제 제품 또는 결과 화면
- 프로젝트명, 기간, 역할
- 해결한 문제를 한 문장으로 요약한 설명
- 핵심 기술 4~6개
- 상세 사례 페이지 링크

대표 이미지로 아키텍처 다이어그램을 사용하지 않는다. 아키텍처는 상세 사례 안에서 보여준다.

### 4.3 경험과 역량

프로젝트 다음에 경력, 교육, 기술 역량을 배치한다. 기술은 단순 나열하지 않고 실제 사용 맥락으로 묶는다.

- Backend: API, 인증, 세션, 데이터 흐름
- Cloud & Platform: Kubernetes, KubeVirt, AWS, GitOps, 관측성
- Frontend: Next.js 기반 사용자 흐름과 상태 UI

실제 근거가 없는 Archive 항목은 제거하거나 공개 가능한 프로젝트로 교체한다.

### 4.4 연락처

페이지 마지막에 이메일, GitHub, 이력서 링크를 다시 제공한다.

## 5. 프로젝트 상세 구조

각 상세 페이지는 프로젝트별 콘텐츠는 달라도 같은 읽기 순서를 유지한다.

1. 프로젝트 제목, 기간, 역할, 팀 규모, 링크
2. 가장 대표적인 실제 화면
3. 프로젝트 배경과 해결하려던 문제
4. 내가 맡은 범위와 책임
5. 주요 기능의 사용자 흐름을 보여주는 큰 화면 2~4개
6. 아키텍처와 요청·데이터 흐름
7. 중요한 기술적 판단과 선택 이유
8. 트러블슈팅: 문제, 원인, 해결, 결과
9. 결과와 회고
10. GitHub, 배포 주소, 관련 문서 등 확인 가능한 근거

섹션마다 동일한 카드 모양을 반복하지 않는다. 큰 이미지, 2열 설명, 전체 폭 본문, 번호가 있는 목록을 콘텐츠에 맞게 조합한다.

## 6. Cledyu 대표 사례

Cledyu 상세 페이지는 다음 사용자 흐름을 중심으로 구성한다.

1. 공개 랜딩에서 서비스 목적 확인
2. Keycloak 기반 로그인
3. Lab 탐색과 난이도 확인
4. 전용 VM 프로비저닝 상태 확인
5. 브라우저 터미널에서 단계 수행
6. Validation Engine을 통한 자동 검증
7. AI 힌트와 학습 진행 상태 확인

아키텍처 설명에서는 Web, Session API, Session Dispatcher, KubeVirt VM, PostgreSQL, Kafka, Validation Engine의 연결을 핵심 흐름으로 보여준다. Vault, ESO, Argo CD, Prometheus, Grafana 등 운영 컴포넌트는 별도의 운영 영역으로 정리한다.

대표 트러블슈팅은 다음처럼 실제 원인과 해결이 확인되는 사례를 우선한다.

- VM 생성 후 터미널 연결 실패: KubeVirt console 조회 RBAC 누락과 RoleBinding 자동 생성 개선
- 여러 창에서 세션 종료가 일관되지 않았던 문제: 세션 수명주기와 클라이언트 상태 동기화
- 프로비저닝 진행률과 실제 상태 불일치: 화면용 시간 기반 수치와 백엔드 상태 단계 분리

## 7. 콘텐츠 데이터 변경

프로젝트 데이터는 화면 렌더링에 필요한 아래 정보를 명시적으로 관리한다.

- `heroImage`: 상세 페이지와 홈에서 사용할 대표 실제 화면
- `challenge`: 프로젝트가 해결한 문제
- `responsibilities`: 개인 담당 범위
- `featureStories`: 이미지, 제목, 설명으로 구성된 주요 기능 흐름
- `outcomes`: 확인 가능한 결과와 배운 점
- `evidence`: GitHub, 배포 주소, 문서 링크

기존 `summary`, `gallery`, `architecture`, `decisions`, `troubleshooting` 데이터는 사실관계를 유지하면서 새 읽기 순서에 맞게 재사용한다.

## 8. 접근성과 반응형

- 모든 실제 이미지에 화면의 목적을 설명하는 대체 텍스트를 제공한다.
- 링크와 버튼에는 키보드 포커스 상태를 제공한다.
- 장식용 요소는 보조기술에서 숨긴다.
- `prefers-reduced-motion` 환경에서는 reveal 이동 효과를 제거한다.
- 768px 이하에서 모든 주요 레이아웃은 단일 열로 바뀐다.
- 데스크톱에서도 본문 한 줄이 지나치게 길어지지 않도록 최대 폭을 제한한다.

## 9. 완료 기준

- 홈 화면에서 Cledyu의 실제 서비스 화면과 백엔드·클라우드 역할이 첫 번째 프로젝트로 보인다.
- 대표 프로젝트마다 실제 화면이 아키텍처보다 먼저 나온다.
- Cledyu 상세 페이지에서 사용자 흐름, 담당 범위, 아키텍처, 트러블슈팅, 결과를 순서대로 확인할 수 있다.
- 기존 프로젝트 경로와 이력서 경로가 유지된다.
- 데스크톱과 모바일에서 가로 스크롤이나 잘린 콘텐츠가 없다.
- `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm test:e2e`가 통과한다.
- 실제 브라우저에서 홈, Cledyu 상세, 다른 프로젝트 상세, 이력서 페이지를 시각적으로 검증한다.

## 10. 범위에서 제외할 내용

- `min-hyuk.com`의 문구, 코드, 이미지 또는 고유한 시각 요소를 그대로 복제하지 않는다.
- CMS나 관리자 화면은 추가하지 않는다.
- 근거가 없는 방문자 수, 성능 향상률, 비용 절감률은 만들지 않는다.
- 현재 개편에 필요하지 않은 새 UI 라이브러리나 애니메이션 의존성을 추가하지 않는다.
